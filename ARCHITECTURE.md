# ARCHITECTURE.md — GuessTheMSG

This is the living technical source of truth for GuessTheMSG (per `CLAUDE.md`'s Workflow section). Update it as schema/architecture decisions are made or changed — don't let it drift from what's actually built. Corresponding migrations live under `supabase/migrations/`, applied via the Supabase MCP server.

**Project status as of this doc:** Supabase project `solqgbkmfyaukdwwdxxm` connected via MCP. Phase 1 (schema + RLS), Phase 2 (Home page, `create-room`/`join-room`, `/room/[code]` stub), Phase 3 (live lobby — Presence, `promote-host`, `start-game`), and Phase 4 (the round loop — `round-tick`, `submit-guess`, live timer, scoring, two-tier chat, recap, results) are all applied and verified — see §4/§5/§7/§11/§14. Verification for each phase combined `curl`/SQL (deterministic authorization cases, real RLS impersonation) with a real two-player browser session — Phase 4's included a genuine live game played to completion across three rounds, a mid-round refresh/reconnect, and a direct REST reproduction of a pre-existing RLS bug this phase's testing surfaced and fixed (§4). `restart-room`/`kick-player`/`cleanup-rooms` (§14) are not yet written.

## 1. Stack

- **Frontend:** Next.js 16 (App Router, TypeScript), server components by default, `'use client'` only where interactivity/state requires it.
- **Styling/UI:** Tailwind CSS + shadcn/ui.
- **Animation:** Framer Motion (entrances, leaderboard reordering), canvas-confetti (win moment), rough-notation (sparse hand-drawn accents).
- **Backend:** Supabase — Postgres (schema + RLS), Realtime (Broadcast + Presence), Auth (anonymous), Edge Functions (Deno) for all trusted logic.
- **Client state:** Zustand for room/game state — no heavier state library.
- **Hosting:** Vercel (frontend) + Supabase Cloud (backend).
- **Avatars:** DiceBear `open-peeps`/`notionists`, ~12 curated seeds pre-rendered to static SVGs at build time.

## 2. Data model

Core tables (Postgres via Supabase). Each ships with its RLS policies in the same migration — never as a follow-up (Non-negotiable rule 4).

- **`rooms`** — `id`, `code` (short human-friendly join code, e.g. `FOX-482`; format enforced by a `rooms_code_format` check constraint, `^[A-Z0-9]{3}-[0-9]{3}$`, charset generated by `create-room` excludes visually-ambiguous `I/L/O`/`0/1`), `name`, `password_hash` (nullable, pgcrypto/`crypt()` — never plaintext), `status` (`lobby` / `in_progress` / `ended`), `category_id`, `settings` (jsonb, always a complete object — see shape below), `created_at`, `last_active_at` (drives the 24h cleanup job). No `host_id` — see `players.is_host` below.

  `rooms.settings` shape, as written by `create-room` (`clampSettings` in `supabase/functions/_shared/settings.ts`, bounds also enforced there — Non-negotiable rule 7):
  ```json
  {
    "rounds": 10,
    "seconds_per_round": 45,
    "max_players": 16,
    "end_round_on_all_correct": true,
    "scoring": { "base_points": 100, "decay_per_second": 5, "min_points": 20, "first_guess_bonus": 25 }
  }
  ```
  Bounds: `rounds` 3–30 (default 10), `seconds_per_round` 15–120 (default 45), `max_players` 2–16 (default 16, not host-editable in the Phase 2 UI — the field exists so `join-room`'s room-full check has a real number to read, and so a later phase can make it host-editable without a migration). `scoring` isn't host-editable at all yet; it's written now so a future `start-round`/`submit-guess` phase has a settled formula rather than inventing one under time pressure.

  A future `start-round`'s word pool for a room is the union of its chosen global category and its own custom category, i.e. `words.category_id IN (rooms.category_id) OR words.category_id IN (SELECT id FROM categories WHERE room_id = rooms.id AND is_custom)` — noted here so it isn't an archaeology problem when that phase is written.
- **`players`** — `id`, `room_id`, `auth_user_id` (Supabase anonymous auth), `display_name`, `avatar_id`, `score`, `is_host` (bool — the single source of truth for who hosts a room; a partial unique index on `(room_id) WHERE is_host` guarantees exactly one per room, which is also why `rooms` carries no `host_id` — two columns claiming to say who's host is how they drift), `is_connected` (bool, server-maintained bookkeeping only — the live lobby UI reads Presence for "connected right now," not this column; see §5/§11), `is_spectator` (bool — true for late joiners until the next round starts), `status` (text: `active` / `kicked`, default `active` — see §10), `is_muted` (bool, default false — see §10), `joined_at`, `last_seen_at` (timestamptz, default `now()` — the host's liveness lease; client-writable, but a `BEFORE UPDATE` trigger always overwrites the value with the server's clock, so the only assertion a client can make is "I'm alive right now," never a post-dated value — see §11).
- **`categories`** — `id`, `name` (Movies, Food, Things, etc.), `is_custom` (bool), `room_id` (nullable — null for global/default categories, set for a room's custom set).
- **`words`** — `id`, `category_id`, `emoji_sequence`, `answer`, `difficulty` (optional). `answer` is never selectable by `anon`/`authenticated` — see §3.
- **`game_sessions`** — `id`, `room_id` (FK `rooms`), `session_number` (int, increments per room starting at 1), `started_at`, `ended_at` (nullable while active), `category_id`, `settings` (jsonb — a snapshot of the room's category/scoring/round settings *at the time this session started*, so a later host reconfiguration doesn't retroactively change what a past session's recap says it was playing). One row per playthrough of a room — see §9 for why this exists.
- **`rounds`** — `id`, `game_session_id` (FK `game_sessions`, not nullable), `room_id`, `word_id`, `emoji_sequence` (a snapshot of `words.emoji_sequence`, copied here at round start — clients read it from `rounds`, never from `words`, so `words` needs no client-facing grant of any kind; see §3), `round_number` (scoped to `game_session_id`: uniqueness is `(game_session_id, round_number)`, not `(room_id, round_number)`), `started_at`, `ends_at` (both server timestamps, written once), `revealed_at` (timestamptz, null while the round is live — this and `revealed_answer` are the only moment the answer becomes client-readable, at the exact instant `round-tick` reveals the round; see §3/§14), `revealed_answer` (text, null until reveal). A unique partial index (`rounds_one_live_per_session on (game_session_id) where revealed_at is null`) guarantees at most one live round per session — the concurrency guard that lets any member's `round-tick` call race safely (§14).
- **`guesses`** — `id`, `round_id`, `player_id`, `guess_text`, `is_correct`, `submitted_at` (server clock, never client-reported), `points_awarded`. A partial unique index enforces one correct guess per player per round at the DB layer — see §7 and §14.
- **`chat_messages`** — `id`, `room_id`, `player_id`, `body`, `created_at`, `kind` (`chat` / `guess` / `system`), `round_id` (nullable — set for any message sent while a round is live, null for lobby/recap/ended chat), `visibility` (`all` / `correct` — the two-tier winners' chat, §4/§14). Guesses and chat share one stream — this is what makes the single chat/guess box in the product spec work. The client renders `kind` differently (correct-guess system rows carry the point value inline, never the answer) rather than using two separate UI widgets. `chat_messages` has no client `insert` grant at all as of Phase 4 — `submit-guess` (§14) is the only writer, so the profanity filter and the winners'-chat split can't be bypassed by a direct PostgREST call. Inserts still require the sending player's `is_muted = false`, enforced inside `submit-guess` now rather than by RLS.

## 3. Never trust the client with the answer (Non-negotiable rule 1)

The naive build sends the round's answer to every client so it can check `guess === answer` locally — don't do this; devtools or a Realtime message payload would leak it before anyone types. Instead:

1. Clients only ever receive `emoji_sequence` for the active round — never `answer`. Concretely: `start-round` snapshots `words.emoji_sequence` onto the new `rounds` row, and clients read it from `rounds` — they never query `words` at all (§2).
2. Guesses go to a `submit-guess` Edge Function, which: looks up the answer with `service_role`, normalizes both strings (trim/lowercase/strip punctuation), checks correctness, stamps `now()` server-side, computes points (§7), writes the `guesses` row, and broadcasts the result.
3. `words` has RLS enabled with **zero** policies for `anon`/`authenticated`, and the table's default grants are explicitly revoked from both roles (§4) — no row is visible to any client role under any query shape, not just `answer`. Only the Edge Function's `service_role` can read it, since `service_role` bypasses RLS entirely. Applied and verified in Phase 1 (`mcp__supabase__execute_sql`, impersonating `authenticated`: `SELECT answer FROM words` → `permission denied for table words`).

## 4. RLS policy shape (per table, applied in the same migration as the table)

**Mechanics common to every table:** Supabase's default privileges grant `anon`/`authenticated` table access in `public` at creation time — RLS alone would leave that blanket grant in place, so every table gets `revoke all on <table> from anon, authenticated` before its (narrow) `grant`s are added back. Every policy is `to authenticated` (anonymous players use the `authenticated` role, not `anon` — §8); `anon` gets no grants anywhere.

Room-membership checks can't be written as a policy on `players` that queries `players` (Postgres raises "infinite recursion detected in policy for relation players"), and every other room-scoped table needs the same check anyway. Three `SECURITY DEFINER` helper functions — `private.is_room_member(room_id)`, `private.is_room_host(room_id)`, `private.is_room_member_of_round(round_id)` — read `players` with RLS bypassed and are called from every room-scoped policy below. They live in a `private` schema (not `public`) with `search_path = ''` pinned and `EXECUTE` granted only to `authenticated`: this keeps them out of PostgREST's exposed API (no `/rest/v1/rpc/is_room_member` route — they're for policies to call internally, not for clients to call directly) and closes the mutable-search-path privilege-escalation vector the security advisor flags on `SECURITY DEFINER` functions.

- **`rooms`**: `select` only, gated on `private.is_room_member(id)`. No client `insert`/`update`/`delete` — room creation, status transitions, and settings changes go through Edge Functions running as `service_role`, which bypasses RLS/grants entirely.
- **`players`**: `select` gated on `private.is_room_member(room_id)`. `update` is restricted two ways at once: an RLS policy requiring `auth_user_id = (select auth.uid())`, *and* a column-level grant covering only `(display_name, avatar_id)` — `score`, `is_host`, `status`, `is_muted`, `is_spectator` are absent from the grant, so a client `UPDATE` touching them is rejected by the privilege system before RLS is even consulted (Non-negotiable rule 4). No client `insert`: joining runs through `join-room` (§14), which is where the password check, max-player cap, and kicked-player check belong.
- **`words`**: no policies at all, for either role — see §3.
- **`game_sessions`**: `select` only, gated on `private.is_room_member(room_id)`. `insert`/`update` (starting/ending a session) are Edge-Function-only (`restart-room`, §14).
- **`rounds`**: `select` only, gated on `private.is_room_member(room_id)`.
- **`guesses`**: `select` only, gated on `private.is_room_member_of_round(round_id)`. No client `insert`: guesses are written only by `submit-guess` (Non-negotiable rule 2).
- **`chat_messages`**: `select` gated on `private.is_room_member(room_id) and (visibility = 'all' or private.has_correct_guess(round_id))` — the winners'-chat split. `private.has_correct_guess(round_id)` (Phase 4, same `SECURITY DEFINER`/`search_path=''` shape as the other helpers) checks whether the calling `auth.uid()` has a correct `guesses` row for that round. Because Realtime `postgres_changes` applies RLS per subscriber, a player who hasn't guessed correctly never *receives* a `visibility='correct'` row over the wire — it isn't client-side filtering of data the browser already has. As of Phase 4 there is **no client `insert` policy at all**: `submit-guess` (§14) is the only writer, using `service_role` — see the `chat_messages` entry in §2 for why the earlier `chat_messages_insert_unmuted` policy was dropped.
- **`categories`**: `select` only; global categories (`room_id is null`) readable by all `authenticated`, custom categories gated on `private.is_room_member(room_id)`.

**Bug found and fixed in Phase 4 — `is_room_member_of_round` was broken since Phase 1.** `private.is_room_member_of_round`'s body still called `public.is_room_member(...)` after an earlier migration (`helper_functions_private_schema`) moved `is_room_member` into the `private` schema. Because the function runs with `set search_path = ''`, that schema-qualified call resolved against a name that no longer existed, so **every** authenticated `SELECT` against `guesses` — the only table this helper gates — failed with `42883 function public.is_room_member(uuid) does not exist`. Nothing surfaced it for three phases because no client code read from `guesses` until Phase 4's round-recap screen became the first caller; reproduced directly against the live REST API (`GET .../rest/v1/guesses?...` → `404 {"code":"42883"}`) before being fixed by a `CREATE OR REPLACE` that corrects the inner call to `private.is_room_member(...)` (migration `20260819050212_fix_is_room_member_of_round.sql`). `CREATE OR REPLACE` preserves the function's OID, so the `guesses_select` policy — which references it by OID, not by name — needed no changes. Note for future `private.*` helpers: an inner call to another moved helper must be updated in the same migration that moves it, not assumed to keep working via `pg_depend`, which only protects the *policy's* reference to a function, not that function's *own* references to others.

**Password hashing functions** (`public.hash_password(password)`, `public.verify_password(password, password_hash)`, added in `supabase/migrations/*_password_functions.sql`): `SECURITY DEFINER`, `search_path = ''`, using `extensions.crypt()`/`extensions.gen_salt('bf', 10)` — the pgcrypto/`crypt()` mechanism Non-negotiable rule 6 names explicitly. Live in `public` (not `private`) because PostgREST only routes RPC for its exposed schemas, and `private` isn't one — `service_role`-only callers (`create-room`, `join-room`) still need a working `.rpc()` call. Locked down with the same two-step Phase 1 learned the hard way: `revoke all ... from public, anon, authenticated` (revoking from the `PUBLIC` pseudo-role alone leaves `anon`/`authenticated`'s own default-privilege grants intact) followed by `grant execute ... to service_role` only. Verified: `set local role authenticated; select public.hash_password('x')` → `permission denied for function hash_password`.

## 5. Realtime channel design

One Supabase Realtime channel per room, topic `room:<code>` (uppercase, matching the URL — `presenceTopic()` in `_shared/presence.ts`), split by concern:

- **Broadcast** — still unused as of Phase 4. Chat/guess messages, round starts, and correct-guess events all turned out to be expressible as `postgres_changes` on already-RLS-gated tables (below), which gets per-subscriber authorization for free — the winners'-chat split specifically depends on that. Revisit if a genuinely ephemeral, non-persisted signal (e.g. typing indicators) is ever added.
- **Presence** — "who's currently connected," driving the live player list and connect/disconnect state without polling. Presence key is `players.id` (not a random UUID) — a refreshing tab's old and new sockets collapse under the same key, so the roster can never show a duplicate. Tracked payload is minimal, `{ playerId }` — nothing durable goes into Presence, the DB owns name/avatar/host/score.
- **Postgres Changes / refetch-on-broadcast** — authoritative state that must survive a refresh or late join, all on the same one-channel-per-room subscription (`use-room-channel.ts`): `players` and `rooms` (filtered `room_id=eq.<id>`/`id=eq.<id>`, since Phase 3), plus `rounds` and `chat_messages` (filtered `room_id=eq.<id>`, since Phase 4). All four filter on a column that never changes for the page's lifetime, so nothing re-subscribes when a round rolls over. A refreshing player reloads the room snapshot — including the latest round and recent chat — from the DB and re-subscribes rather than losing state.

**Channel privacy (Phase 3 decision):** public (Supabase default), not RLS-gated. Enforcing a private channel requires disabling "Allow public access" in the Dashboard's Realtime Settings *and* adding RLS policies on `realtime.messages` — deferred to whenever chat lands, since chat's broadcast payload (message content) is the actually sensitive thing; Presence alone only leaks room membership/online-status for a 6-character code that isn't trivially guessable. Revisit this note when chat is built rather than treating it as settled.

## 6. Round timing — server-authoritative (Non-negotiable rule 3)

The client never counts down from a locally-set duration. On round start, `round-tick` (§14) writes `started_at`/`ends_at` (server timestamps, computed from `settings.seconds_per_round`) once; every client's countdown is `ends_at - (Date.now() + serverOffsetMs)`, continuously recomputed. `serverOffsetMs` corrects for client clock skew — sampled once per round from the gap between a freshly-inserted round's `started_at` and the client's own `Date.now()` at the moment the INSERT arrives (`use-room-channel.ts`), not applied to the catch-up read (where `started_at` is legitimately in the past). This keeps all players in sync regardless of clock drift/latency and makes "who guessed first" ordering fair and non-disputable, since it's decided by server-received `submitted_at` (`submit-guess`, §14), never a client-reported time.

## 7. Scoring model (tunable default, stored per-room)

- Base points per round (default 100), decaying with elapsed time (default `max(20, 100 - 5*seconds_elapsed)`) — faster guesses score more.
- First correct guesser gets a flat bonus on top (default +25) — the "first guesser scores more" mechanic from the product spec.
- Only a player's *first* correct guess per round counts — no farming extra points by re-submitting after already succeeding. This is enforced at the DB layer, not just in application code — see the partial unique index in §14.
- Recap and end-of-game stats (fastest average guess time, most correct guesses, MVP, per-round breakdown) are computed by joining through `rounds.game_session_id`, not just `room_id` — a restarted room has multiple `game_sessions`, and a naive `room_id`-only query would blend a new game's stats with a prior one's (see §9).
- Round ends on timer expiry, or (if `rooms.settings` enables it) once every connected, non-spectating player has guessed correctly.
- The formula itself lives in `rooms.settings`, tunable per room without a code change — also the natural extension point for future game modes (e.g. a harsher-decay "speed mode").
- Server validates `settings` on write (rounds count, seconds/round, scoring params) against sane min/max bounds — a malformed or adversarial request (`rounds: 0`, negative seconds) fails gracefully rather than corrupting the room (Non-negotiable rule 7).

## 8. Auth, sessions, and reconnect

- Supabase anonymous auth issues a session per browser tab/device on first Home-screen action.
- Room code + session are persisted in `localStorage`. On load, if both are present and the room/player still exist, the client rejoins the same `players` row (updating `is_connected`) instead of creating a duplicate — this is what makes refresh-mid-game safe. Before resuming the seat, the rejoin check reads `players.status` first: if it's `kicked`, the rejoin is refused (see §10) rather than resuming.
- Presence drift (tab closed without a clean disconnect event) is reconciled via a heartbeat/timeout rather than an instant flip to disconnected, to avoid flickering state on flaky mobile networks. Concretely: a player only renders as "disconnected" after `DISCONNECT_UI_GRACE_MS` (5s) of continuous absence from Presence — a page refresh (~0.5–2s) never flickers to disconnected for other viewers. All timing constants live in `supabase/functions/_shared/presence.ts`, imported by both the client (via `@shared/presence`) and any future server-side use, so there's one number to retune, not several hand-synced copies.

## 9. Game sessions — restart session boundary

`rounds`/`guesses` are not scoped to `room_id` alone. A room can be restarted (§14 `restart-room`), and each playthrough is its own `game_sessions` row — `rounds.game_session_id` is what actually disambiguates "round 1 of this game" from "round 1 of the previous game in the same room."

- `start-game` (§14) creates the room's **first** `game_sessions` row (`session_number = 1`) the moment `rooms.status` leaves `lobby`; `restart-room` creates each subsequent one (`session_number` + 1). Both snapshot the room's *current* `category_id`/`settings` into the session, rather than zeroing/reusing the previous game's `rounds`/`guesses` rows. `start-game` claims the `rooms.status` transition first (`update ... where status='lobby'`) and only inserts the session if it wins that race, so two simultaneous host clicks can never produce two sessions for the same game.
- Prior `rounds`/`guesses` rows are left untouched, still attached to their original `game_session_id` — this is what keeps per-round recap, fastest-average-guess-time, most-correct-guesses, MVP, and per-round breakdown correct after a restart (§7), and incidentally sets up a "past games in this room" view later without any schema change.
- `players.score` is reset to 0 on restart; `players` rows themselves persist across sessions (same room, same seats) — restart does not re-create players.

## 10. Kick vs. mute

Kick and mute are different actions with different enforcement points, both host-only (`DESIGN.md` §5):

- **Mute** (`players.is_muted`): stops a player from posting to `chat_messages`. Enforced in the RLS `insert` policy on `chat_messages` (§4), not just hidden in the client — a muted player's guesses (written server-side via `submit-guess`, §14) are unaffected; mute is about chat noise, not gameplay.
- **Kick** (`players.status = 'kicked'`): removes the player from active participation and blocks the automatic `localStorage` rejoin described in §8. A `kick-player` Edge Function (§14, host-only) sets `status = kicked` and `is_connected = false`, and broadcasts a removal event so the kicked client is redirected out immediately rather than waiting for their next action to fail.
- This only blocks the *same* browser session from silently walking back in; it doesn't prevent a determined player from rejoining with a fresh anonymous session. See the open question in §16.

## 11. Host migration

Implemented via a DB-verifiable **host lease**, not a client-side election — a client-observed "the host seems gone" signal is never enough on its own to authorize a state change (rule 7); the server always re-derives who should be host from data it can verify independently.

**Mechanism:** only the current host's client heartbeats — `update players set last_seen_at = now() where id = <my player id>` every `HEARTBEAT_INTERVAL_MS` (5s), plus immediately on mount/becoming-host/`visibilitychange → visible`. The value sent is irrelevant; a `BEFORE UPDATE` trigger on `players` always overwrites it with the server's own clock (§2), so a client's only expressible assertion is "I'm alive right now" — it can never post-date the lease to keep the room hostless, or claim liveness in the past. Everyone else's client runs a **watchdog**: once Presence has synced and the host is absent from it, a timer arms — `HOST_GRACE_MS` (18s) if the watching client is itself the presumptive successor (earliest `joined_at` among eligible remaining players — "longest-connected" means **seat age, not socket age**, so a refresh never resets seniority), or `HOST_GRACE_MS` + 3–5s of random jitter otherwise (a herd-breaker, so multiple eligible clients don't all fire `promote-host` simultaneously). If the host row is missing entirely, the shorter `HOST_ORPHAN_GRACE_MS` (3s) applies. On fire, the watching client calls the `promote-host` Edge Function (§14), which is the only place `is_host` is actually written: it independently re-reads `players.last_seen_at` and only allows the transition if the lease is truly stale (`≥ HOST_LEASE_MS`, 15s — 3 missed heartbeats) or the caller *is* the current host (voluntary self-demotion, providable from the JWT, never an escalation) — a live host's own heartbeat is the veto, so a lying client gains nothing by calling this early. `HOST_STILL_ACTIVE` is returned otherwise, and the watchdog retries at `HOST_PROMOTE_RETRY_MS` (5s) up to 4 times.

Invariants if any of these are retuned: `HOST_LEASE_MS ≥ 3 × HEARTBEAT_INTERVAL_MS` (tolerate two lost beats on flaky mobile); `HOST_GRACE_MS ≥ HOST_LEASE_MS + HEARTBEAT_INTERVAL_MS` (the first `promote-host` call shouldn't fire against a lease that isn't stale yet); `DISCONNECT_UI_GRACE_MS < HOST_LEASE_MS` (§8 — the dot goes grey before the badge moves, so a migration reads as a consequence in the UI, not a surprise). Worst-case migration latency end-to-end is ~18–20s, narrated in the lobby UI the whole time ("Host disconnected — picking a new host…").

**Rejected:** a departing host's `pagehide` handler firing an immediate hand-off. `pagehide` can't distinguish "closing the tab" from "hitting refresh," so it would hand off the crown on every host refresh — exactly the bug the lease design exists to avoid. A "Leave room" button doing a deliberate voluntary hand-off is supported by `promote-host` already (see §14) but has no UI yet — a later phase.

The UI reflects the change as soon as `players.is_host` changes (Postgres Changes on `players`, §5) — no extra broadcast needed. A "system chat message" per the original draft of this section is deferred until chat exists; today it's a badge move plus a transient inline line in the lobby.

## 12. Late joiners

Joining is allowed at any room `status`. If `status = in_progress`, the new `players` row is created with `is_spectator = true`; the Edge Function/RLS layer prevents spectators from calling `submit-guess`. When the current round ends and the next one starts, spectators flip to full players automatically.

## 13. Room lifecycle & cleanup

- Rooms inactive beyond ~24h (`last_active_at` unchanged) are cleaned up by a scheduled Supabase Edge Function / `pg_cron` job — otherwise `rooms` grows unbounded with stale data.
- Server-enforced caps: max players per room, min/max rounds, min/max seconds per round (same validation point as §7).
- Word selection is no-repeat within a session and shuffled per room, so two rooms playing the same category don't see identical sequences.

## 14. Edge Functions (all trusted game logic — Non-negotiable rules 1, 2, 5)

Each uses `service_role` server-side only, never exposed to the client bundle. `create-room`, `join-room`, `promote-host`, `start-game`, `round-tick`, and `submit-guess` are implemented; `restart-room`/`kick-player`/`cleanup-rooms` are not yet written.

**`round-tick` replaces the separately-planned `start-round`/`advance-round` pair.** One idempotent state machine — create round 1, reveal a round that's due, advance past the recap, end the game — instead of two functions with duplicated precondition checks. It is callable by **any active room member, not just the host**, which is a deliberate departure from the original plan and is worth understanding before "hardening" it back to host-only:

- `round-tick` holds no privilege. Every transition it makes is re-derived from server state and server time (`now >= ends_at`, all-correct, recap elapsed) — a caller can only ask "is anything due?", never assert that something is. A host-only gate would therefore have protected nothing.
- It closes a real failure mode a host-only design has: a host who merely **backgrounds** their tab (alt-tabs, checks their phone — plausible mid-party) keeps their WebSocket alive, so Presence never drops and the host-migration watchdog (§11) never arms, while the browser throttles a backgrounded `setInterval` to roughly once a minute. A host-only ticker would stall the round for up to that long with no failover.
- The client (`use-round-tick.ts`) fires a tick only when a transition is actually due (computed from `serverOffsetMs`), plus a 5s safety poll and an immediate tick on `visibilitychange → visible` — in steady state this is close to zero requests, not a fixed-interval poll from every client.
- Concurrency is a DB concern, not a locking concern here: `rounds_one_live_per_session` and the existing `(game_session_id, round_number)` uniqueness make a duplicate `createRound` call from two racing clients a caught `23505` that re-reads and converges; `reveal` uses `where revealed_at is null` so the loser of a race no-ops.

**`submit-guess`** is the only path every message from the combined chat/guess input takes — chat, wrong guesses, and correct guesses alike — which is what makes the winners'-chat split and the profanity filter unconditional rather than something a client could route around. Gate ordering is deliberate: the guess is compared against the answer **before** the profanity filter runs, and an exact normalized match to the answer is exempted from the filter entirely. A profanity-first ordering would mean a seeded word that happens to trip the filter makes that round silently unwinnable for everyone, with no visible cause — the `guess.test.deno.ts` self-check asserts no seeded answer trips the filter as a backstop, but the ordering is what makes that assertion load-bearing rather than merely reassuring. A correct guess is also never republished verbatim (the broadcast is `"<name> guessed correctly +<points>"`), so there's nothing for the filter to protect on that path anyway.

**Profanity filter narrowed to a single term.** `_shared/profanity.ts` no longer builds `obscenity`'s full `englishDataset` — it now blocks exactly the n-word and its obfuscations (leetspeak, spacing, letter repetition), keeping `obscenity`'s transformer pipeline (the load-bearing part) but replacing the word list with one entry copied verbatim from upstream's own definition, including its `snigger` whitelist. Ordinary profanity is allowed. This affects every existing caller of `containsProfanity` unchanged in signature — display names, room names, custom words — not just chat.

**Response envelope** (`supabase/functions/_shared/errors.ts`), shared by every function: `{ ok: true, data }` or `{ ok: false, error: { code, message, fields? } }`. Deliberately HTTP 200 for expected *domain* outcomes (validation, wrong password, room full, kicked) — only auth failures (401) and genuine faults (500) get a non-2xx status, since `supabase.functions.invoke()` throws on any non-2xx and buries the body behind `err.context.json()`.

| Code | HTTP | Meaning |
|---|---|---|
| `UNAUTHENTICATED` | 401 | no/invalid JWT |
| `METHOD_NOT_ALLOWED` | 405 | non-POST |
| `VALIDATION_ERROR` | 200 | `fields` maps field → message |
| `PROFANITY_BLOCKED` | 200 | `fields` names the offending field(s) — checked on room name, custom words (both sides), display name, and (Phase 4) every chat/guess message via `submit-guess`. The filter itself blocks one slur, not general profanity — see §14's `round-tick`/`submit-guess` section |
| `CATEGORY_NOT_FOUND` | 200 | create-room: `categoryId` isn't a real global category (blocks pointing a new room at another room's private custom category) |
| `ROOM_NOT_FOUND` | 200 | join-room: bad code format or no such room — deliberately not distinguished, no format-probing signal to leak |
| `PASSWORD_REQUIRED` | 200 | room is protected, none supplied |
| `INVALID_PASSWORD` | 200 | wrong password |
| `ROOM_FULL` | 200 | active players ≥ `settings.max_players` |
| `KICKED` | 200 | existing player row has `status='kicked'` |
| `CODE_GENERATION_FAILED` | 500 | 5 collision retries exhausted |
| `NOT_A_MEMBER` | 200 | `promote-host`/`start-game`: caller has no seat in this room |
| `NOT_HOST` | 200 | `start-game`: caller isn't the current host (checked from their own DB row, never a body flag) |
| `NOT_ENOUGH_PLAYERS` | 200 | `start-game`: fewer than `MIN_PLAYERS_TO_START` (2) active, non-spectating players |
| `HOST_STILL_ACTIVE` | 200 | `promote-host`: the current host's lease hasn't expired — the veto that makes the function safe against a lying caller |
| `INVALID_ROOM_STATE` | 200 | `start-game`: room already `ended`, or the `lobby→in_progress` transition was already claimed by a concurrent call |
| `INTERNAL_ERROR` | 500 | anything unhandled |

- `create-room` — validates + profanity-checks display/room name and custom words, clamps settings, verifies the category, hashes the password (if any), generates the room code with a collision-retry loop (catches `23505`, regenerates, ≤5 attempts), creates the room + optional custom category/words + host player. Any failure after the room insert triggers a compensating delete (`ON DELETE CASCADE` cleans up categories/words/players in one statement) — supabase-js has no cross-table transaction primitive, and moving this into a single SQL function would pull trusted logic out of the testable `_shared/` modules, so this is a deliberate trade-off, not a shortcut.
- `join-room` — looks up the room by normalized code, checks for an existing `players` row *before* the password gate: a `kicked` status short-circuits to `KICKED`; an existing **active** seat skips the password check entirely and goes straight to a rejoin update. This is deliberate: the existing seat is proof the password (if any) was already satisfied once, and it's what makes DESIGN.md §2.9's silent-refresh-reconnect promise work without re-prompting for a password on every refresh. New joins get `is_spectator = true` when `room.status !== 'lobby'` (§12/§2.7), and never `is_host: true` (the `players_one_host_per_room` partial unique index would reject it anyway — the schema backstopping the application logic). A `23505` race on the seat's unique constraint falls through to the same rejoin-update path rather than failing.
- `promote-host` — "ensure this room has a live host," idempotent, callable by any seated member. Recomputes the successor entirely server-side (`pickSuccessor` in `_shared/presence.ts` — earliest `joined_at` among eligible, fresh-lease-first tiebreak); the request carries no `newHostPlayerId`, so a client cannot name who becomes host. Authorizes exactly two ways: the caller *is* the current host (voluntary self-demotion) or the current host's `last_seen_at` lease has expired (§11). Demote/promote are two separate `UPDATE`s, both re-checking their precondition in the `WHERE` clause (not just an earlier `SELECT`) so a heartbeat or a competing `promote-host` call landing mid-request loses the race cleanly rather than corrupting state; a `23505` on the promote step (partial unique index) means someone else already won, and the function just reports the current truth instead of erroring.
- `start-game` — host-only `rooms.status: 'lobby' → 'in_progress'`, creating the room's first `game_sessions` row (§9). Claims the status transition first (`update ... where status = 'lobby'`) and only inserts the session if it wins that race — idempotent on a double-click, returns the existing session rather than erroring. Deliberately does not pick a word, write round timing, or broadcast a round; that's `start-round` below, a later phase. Note the client/server asymmetry: the Start button is gated on ≥2 *presence-present* players (accurate, presence is client-visible) while the server floor is ≥2 *seated* players (conservative, the server can't see presence) — the UI is strictly stricter, the server floor exists so a forged invoke still can't start a 1-player game.
- `round-tick` — see the dedicated section above. Selects the next word (no-repeat within the session, shuffled — pool is the union of the session's category and the room's custom category, §2's word-pool contract), writes `started_at`/`ends_at`, flips any spectators in at a round boundary (§12), reveals a due round (writes `revealed_at`/`revealed_answer`), and ends the game (`rooms.status = 'ended'`, `game_sessions.ended_at`) once the configured round count is reached or the word pool runs dry.
- `submit-guess` — the core function described in §3, and see the dedicated section above for gate ordering and why it's the sole `chat_messages` writer. A partial unique index enforces the invariant from §7:
  ```sql
  CREATE UNIQUE INDEX guesses_one_correct_per_player_round
    ON guesses (round_id, player_id)
    WHERE is_correct = true;
  ```
  This closes the race between two near-simultaneous requests from the same player that could otherwise both evaluate "not yet correct" before either write lands and double-award the first-guess bonus. The function catches the resulting unique-violation as an expected "already answered correctly" outcome — returns the existing result, awards no additional points — rather than surfacing it as an unhandled error. First place is decided *after* the insert, by ordering the persisted `guesses` rows by `submitted_at`, not by a pre-insert count — the same race, one level up: two players racing each other must not both read "zero correct guesses so far" and both claim the first-guess bonus.
- `restart-room` — creates a new `game_sessions` row and resets `players.score`, per §9. Does not touch or delete prior `rounds`/`guesses`.
- `kick-player` — host-only; sets the target player's `status = 'kicked'`, `is_connected = false`, and broadcasts a removal event (§10).
- `cleanup-rooms` — scheduled, per §13.

## 15. Pure logic vs. network code

Scoring formulas and string normalization are unit-testable independent of any Edge Function or UI (Coding conventions) — but "lives in `lib/`" turned out to mean something more specific once Edge Functions actually existed. Deno (Edge Functions) and Next can't share a plain `src/lib/` module directly, and `mcp__supabase__deploy_edge_function` only bundles files under a function's own upload set, so the canonical home is **`supabase/functions/_shared/`**: self-contained modules (no relative imports of their own, Web-API-only, no `Deno.*`/`node:*`) imported by Deno via relative path (`../_shared/settings.ts`) and by Next via the `@shared/*` tsconfig path pointing at the same directory. `room-code.ts`, `settings.ts`, `custom-words.ts`, `validation.ts`, `avatars.ts`, `profanity.ts`, `errors.ts`, `cors.ts`, `presence.ts` all live here; `supabase-admin.deno.ts` is the one Deno-only exception (`.deno.ts` suffix, excluded from Next's `tsc`). Edge Functions import from here rather than reimplementing logic inline, and the same modules back the client-side live-preview validation in the Create Room form — client and server parse/validate identically because it's the same code, not a hand-synced copy.

## 16. Open technical questions
- Rate limiting on `submit-guess` (per-player, per-round) to prevent guess-spam abuse — related to, but distinct from, the DB-enforced "one correct guess per player per round" invariant in §14, since it's about request volume rather than correctness double-counting. Slightly more live now that `round-tick` is member-callable too (still no privilege gained by spamming it, but it's additional request volume worth having an eye on).
- Whether a `kicked` player should be permanently blocked from rejoining via a *new* browser session (different `auth_user_id`, same person) — `players.status` (§10) only stops the same session from walking back in, not a determined re-joiner. Left open pending a decision on how strict v1 moderation needs to be.
- Anonymous sign-in abuse prevention: Supabase's own guidance recommends CAPTCHA/Turnstile on anonymous sign-ups before going public, since each `signInAnonymously()` call creates a real `auth.users` row (default-rate-limited to 30/hour per IP, adjustable in the Dashboard). Not needed for local development/testing, but worth doing before a room link gets shared widely.
- Rich end-of-game stats (fastest average guess time, most correct guesses, MVP, per-round breakdown — §7) are still unbuilt; the results screen as of Phase 4 shows only the final leaderboard. The data is fully queryable through `rounds.game_session_id` when this is picked up.
- `restart-room` and a host reconfigure/restart flow don't exist yet — the results screen is a terminal state for the room as of Phase 4.

## 17. Stack adoption timing (deviation from §1, recorded not silently skipped)

Zustand and Framer Motion, named in §1, were adopted in Phase 4 as planned — the round loop's timer, leaderboard, and chat stream are exactly the shared-state-plus-coordinated-animation case they were deferred for. `src/lib/room/store.ts` is a single module-level Zustand store (one room per page load, so no per-room instancing); `useRoomChannel` writes into it, components read via selectors. One sharp edge worth recording: a selector that builds a fresh array on every call (e.g. `Array.from(map.values()).filter(...)`) breaks React's `useSyncExternalStore` snapshot-caching contract and produces an actual "getSnapshot should be cached" render loop, not just a lint nit — wrap it in `useShallow` from `zustand/react/shallow` (see `leaderboard.tsx`/`game-results.tsx`), or select the raw `Map`/array and derive in a `useMemo` instead.
