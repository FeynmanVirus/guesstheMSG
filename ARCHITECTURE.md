# ARCHITECTURE.md — GuessTheMSG

This is the living technical source of truth for GuessTheMSG (per `CLAUDE.md`'s Workflow section). Update it as schema/architecture decisions are made or changed — don't let it drift from what's actually built. Corresponding migrations live under `supabase/migrations/`, applied via the Supabase MCP server.

**Project status as of this doc:** Supabase project `solqgbkmfyaukdwwdxxm` connected via MCP. Phase 1 (schema + RLS) and Phase 2 (Home page, `create-room`/`join-room` Edge Functions, `/room/[code]` lobby stub) are both applied and verified — see §4 and §14 for what's live. **Anonymous auth is still off in the Dashboard** (Authentication → Providers → Anonymous — no MCP tool reaches this setting) — every RLS policy is `to authenticated`, so nothing in the app can sign in until it's toggled on. This blocked live end-to-end testing of the two Edge Functions during Phase 2; everything short of that (migration correctness, RLS regression, deployed file bundles, build/lint/typecheck) was verified instead. `start-round`/`submit-guess`/`advance-round`/`restart-room`/`kick-player`/`cleanup-rooms` (§14) are not yet written.

## 1. Stack

- **Frontend:** Next.js 16 (App Router, TypeScript), server components by default, `'use client'` only where interactivity/state requires it.
- **Styling/UI:** Tailwind CSS + shadcn/ui.
- **Animation:** Framer Motion (entrances, leaderboard reordering), canvas-confetti (win moment), rough-notation (sparse hand-drawn accents).
- **Backend:** Supabase — Postgres (schema + RLS), Realtime (Broadcast + Presence), Auth (anonymous), Edge Functions (Deno) for all trusted logic.
- **Client state:** Zustand for room/game state — no heavier state library.
- **Hosting:** Vercel (frontend) + Supabase Cloud (backend).
- **Avatars:** DiceBear `open-peeps`/`notionists`, ~12 curated seeds pre-rendered to static SVGs at build time.

## 2. Data model

Core tables (Postgres via Supabase). Each ships with its RLS policies in the same migration — never as a follow-up (Non-negotiable rule 4).

- **`rooms`** — `id`, `code` (short human-friendly join code, e.g. `FOX-482`; format enforced by a `rooms_code_format` check constraint, `^[A-Z0-9]{3}-[0-9]{3}$`, charset generated by `create-room` excludes visually-ambiguous `I/L/O`/`0/1`), `name`, `password_hash` (nullable, pgcrypto/`crypt()` — never plaintext), `status` (`lobby` / `in_progress` / `ended`), `category_id`, `settings` (jsonb, always a complete object — see shape below), `created_at`, `last_active_at` (drives the 24h cleanup job). No `host_id` — see `players.is_host` below.

  `rooms.settings` shape, as written by `create-room` (`clampSettings` in `supabase/functions/_shared/settings.ts`, bounds also enforced there — Non-negotiable rule 7):
  ```json
  {
    "rounds": 10,
    "seconds_per_round": 45,
    "max_players": 16,
    "end_round_on_all_correct": true,
    "scoring": { "base_points": 100, "decay_per_second": 5, "min_points": 20, "first_guess_bonus": 25 }
  }
  ```
  Bounds: `rounds` 3–30 (default 10), `seconds_per_round` 15–120 (default 45), `max_players` 2–16 (default 16, not host-editable in the Phase 2 UI — the field exists so `join-room`'s room-full check has a real number to read, and so a later phase can make it host-editable without a migration). `scoring` isn't host-editable at all yet; it's written now so a future `start-round`/`submit-guess` phase has a settled formula rather than inventing one under time pressure.

  A future `start-round`'s word pool for a room is the union of its chosen global category and its own custom category, i.e. `words.category_id IN (rooms.category_id) OR words.category_id IN (SELECT id FROM categories WHERE room_id = rooms.id AND is_custom)` — noted here so it isn't an archaeology problem when that phase is written.
- **`players`** — `id`, `room_id`, `auth_user_id` (Supabase anonymous auth), `display_name`, `avatar_id`, `score`, `is_host` (bool — the single source of truth for who hosts a room; a partial unique index on `(room_id) WHERE is_host` guarantees exactly one per room, which is also why `rooms` carries no `host_id` — two columns claiming to say who's host is how they drift), `is_connected` (bool, driven by Presence), `is_spectator` (bool — true for late joiners until the next round starts), `status` (text: `active` / `kicked`, default `active` — see §10), `is_muted` (bool, default false — see §10), `joined_at`.
- **`categories`** — `id`, `name` (Movies, Food, Things, etc.), `is_custom` (bool), `room_id` (nullable — null for global/default categories, set for a room's custom set).
- **`words`** — `id`, `category_id`, `emoji_sequence`, `answer`, `difficulty` (optional). `answer` is never selectable by `anon`/`authenticated` — see §3.
- **`game_sessions`** — `id`, `room_id` (FK `rooms`), `session_number` (int, increments per room starting at 1), `started_at`, `ended_at` (nullable while active), `category_id`, `settings` (jsonb — a snapshot of the room's category/scoring/round settings *at the time this session started*, so a later host reconfiguration doesn't retroactively change what a past session's recap says it was playing). One row per playthrough of a room — see §9 for why this exists.
- **`rounds`** — `id`, `game_session_id` (FK `game_sessions`, not nullable), `room_id`, `word_id`, `emoji_sequence` (a snapshot of `words.emoji_sequence`, copied here at round start — clients read it from `rounds`, never from `words`, so `words` needs no client-facing grant of any kind; see §3), `round_number` (scoped to `game_session_id`: uniqueness is `(game_session_id, round_number)`, not `(room_id, round_number)`), `started_at`, `ends_at` (both server timestamps, written once), `revealed` (bool).
- **`guesses`** — `id`, `round_id`, `player_id`, `guess_text`, `is_correct`, `submitted_at` (server clock, never client-reported), `points_awarded`. A partial unique index enforces one correct guess per player per round at the DB layer — see §7 and §14.
- **`chat_messages`** — `id`, `room_id`, `player_id`, `body`, `created_at`, `kind` (`chat` / `guess` / `system`). Guesses and chat share one stream — this is what makes the single chat/guess box in the product spec work; the client renders `kind` differently (e.g. correct guesses highlighted with their point value) rather than using two separate UI widgets. Inserts require the sending player's `is_muted = false` — see §4.

## 3. Never trust the client with the answer (Non-negotiable rule 1)

The naive build sends the round's answer to every client so it can check `guess === answer` locally — don't do this; devtools or a Realtime message payload would leak it before anyone types. Instead:

1. Clients only ever receive `emoji_sequence` for the active round — never `answer`. Concretely: `start-round` snapshots `words.emoji_sequence` onto the new `rounds` row, and clients read it from `rounds` — they never query `words` at all (§2).
2. Guesses go to a `submit-guess` Edge Function, which: looks up the answer with `service_role`, normalizes both strings (trim/lowercase/strip punctuation), checks correctness, stamps `now()` server-side, computes points (§7), writes the `guesses` row, and broadcasts the result.
3. `words` has RLS enabled with **zero** policies for `anon`/`authenticated`, and the table's default grants are explicitly revoked from both roles (§4) — no row is visible to any client role under any query shape, not just `answer`. Only the Edge Function's `service_role` can read it, since `service_role` bypasses RLS entirely. Applied and verified in Phase 1 (`mcp__supabase__execute_sql`, impersonating `authenticated`: `SELECT answer FROM words` → `permission denied for table words`).

## 4. RLS policy shape (per table, applied in the same migration as the table)

**Mechanics common to every table:** Supabase's default privileges grant `anon`/`authenticated` table access in `public` at creation time — RLS alone would leave that blanket grant in place, so every table gets `revoke all on <table> from anon, authenticated` before its (narrow) `grant`s are added back. Every policy is `to authenticated` (anonymous players use the `authenticated` role, not `anon` — §8); `anon` gets no grants anywhere.

Room-membership checks can't be written as a policy on `players` that queries `players` (Postgres raises "infinite recursion detected in policy for relation players"), and every other room-scoped table needs the same check anyway. Three `SECURITY DEFINER` helper functions — `private.is_room_member(room_id)`, `private.is_room_host(room_id)`, `private.is_room_member_of_round(round_id)` — read `players` with RLS bypassed and are called from every room-scoped policy below. They live in a `private` schema (not `public`) with `search_path = ''` pinned and `EXECUTE` granted only to `authenticated`: this keeps them out of PostgREST's exposed API (no `/rest/v1/rpc/is_room_member` route — they're for policies to call internally, not for clients to call directly) and closes the mutable-search-path privilege-escalation vector the security advisor flags on `SECURITY DEFINER` functions.

- **`rooms`**: `select` only, gated on `private.is_room_member(id)`. No client `insert`/`update`/`delete` — room creation, status transitions, and settings changes go through Edge Functions running as `service_role`, which bypasses RLS/grants entirely.
- **`players`**: `select` gated on `private.is_room_member(room_id)`. `update` is restricted two ways at once: an RLS policy requiring `auth_user_id = (select auth.uid())`, *and* a column-level grant covering only `(display_name, avatar_id)` — `score`, `is_host`, `status`, `is_muted`, `is_spectator` are absent from the grant, so a client `UPDATE` touching them is rejected by the privilege system before RLS is even consulted (Non-negotiable rule 4). No client `insert`: joining runs through `join-room` (§14), which is where the password check, max-player cap, and kicked-player check belong.
- **`words`**: no policies at all, for either role — see §3.
- **`game_sessions`**: `select` only, gated on `private.is_room_member(room_id)`. `insert`/`update` (starting/ending a session) are Edge-Function-only (`restart-room`, §14).
- **`rounds`**: `select` only, gated on `private.is_room_member(room_id)`.
- **`guesses`**: `select` only, gated on `private.is_room_member_of_round(round_id)`. No client `insert`: guesses are written only by `submit-guess` (Non-negotiable rule 2).
- **`chat_messages`**: `select` gated on `private.is_room_member(room_id)`. `insert` is gated on `kind = 'chat'` (a client can't forge a `guess`/`system` row) **and** an `exists` check that the inserted `player_id` belongs to the calling `auth.uid()`, in that room, `status = 'active'`, `is_muted = false` — enforced in the policy itself, not hidden client-side, so a muted player can't bypass it by calling PostgREST directly.
- **`categories`**: `select` only; global categories (`room_id is null`) readable by all `authenticated`, custom categories gated on `private.is_room_member(room_id)`.

**Password hashing functions** (`public.hash_password(password)`, `public.verify_password(password, password_hash)`, added in `supabase/migrations/*_password_functions.sql`): `SECURITY DEFINER`, `search_path = ''`, using `extensions.crypt()`/`extensions.gen_salt('bf', 10)` — the pgcrypto/`crypt()` mechanism Non-negotiable rule 6 names explicitly. Live in `public` (not `private`) because PostgREST only routes RPC for its exposed schemas, and `private` isn't one — `service_role`-only callers (`create-room`, `join-room`) still need a working `.rpc()` call. Locked down with the same two-step Phase 1 learned the hard way: `revoke all ... from public, anon, authenticated` (revoking from the `PUBLIC` pseudo-role alone leaves `anon`/`authenticated`'s own default-privilege grants intact) followed by `grant execute ... to service_role` only. Verified: `set local role authenticated; select public.hash_password('x')` → `permission denied for function hash_password`.

## 5. Realtime channel design

One Supabase Realtime channel per room (`room:<code>`), split by concern:

- **Broadcast** — ephemeral, high-frequency: chat/guess messages, "round started" (emoji sequence + `ends_at`), "player X guessed correctly" celebration events, typing indicators.
- **Presence** — "who's currently connected," driving the live player list and connect/disconnect state without polling.
- **Postgres Changes / refetch-on-broadcast** — authoritative state that must survive a refresh or late join: room settings, player scores, round history. A refreshing player reloads the room snapshot from the DB and re-subscribes rather than losing state.

## 6. Round timing — server-authoritative (Non-negotiable rule 3)

The client never counts down from a locally-set duration. On round start, the server (Edge Function, or a Postgres trigger invoked by one) writes `started_at`/`ends_at` (server timestamps) and broadcasts them. Every client's countdown is `ends_at - Date.now()`, continuously recomputed — this keeps all players in sync regardless of clock drift/latency and makes "who guessed first" ordering fair and non-disputable, since it's decided by server-received `submitted_at`, never a client-reported time.

## 7. Scoring model (tunable default, stored per-room)

- Base points per round (default 100), decaying with elapsed time (default `max(20, 100 - 5*seconds_elapsed)`) — faster guesses score more.
- First correct guesser gets a flat bonus on top (default +25) — the "first guesser scores more" mechanic from the product spec.
- Only a player's *first* correct guess per round counts — no farming extra points by re-submitting after already succeeding. This is enforced at the DB layer, not just in application code — see the partial unique index in §14.
- Recap and end-of-game stats (fastest average guess time, most correct guesses, MVP, per-round breakdown) are computed by joining through `rounds.game_session_id`, not just `room_id` — a restarted room has multiple `game_sessions`, and a naive `room_id`-only query would blend a new game's stats with a prior one's (see §9).
- Round ends on timer expiry, or (if `rooms.settings` enables it) once every connected, non-spectating player has guessed correctly.
- The formula itself lives in `rooms.settings`, tunable per room without a code change — also the natural extension point for future game modes (e.g. a harsher-decay "speed mode").
- Server validates `settings` on write (rounds count, seconds/round, scoring params) against sane min/max bounds — a malformed or adversarial request (`rounds: 0`, negative seconds) fails gracefully rather than corrupting the room (Non-negotiable rule 7).

## 8. Auth, sessions, and reconnect

- Supabase anonymous auth issues a session per browser tab/device on first Home-screen action.
- Room code + session are persisted in `localStorage`. On load, if both are present and the room/player still exist, the client rejoins the same `players` row (updating `is_connected`) instead of creating a duplicate — this is what makes refresh-mid-game safe. Before resuming the seat, the rejoin check reads `players.status` first: if it's `kicked`, the rejoin is refused (see §10) rather than resuming.
- Presence drift (tab closed without a clean disconnect event) is reconciled via a heartbeat/timeout rather than an instant flip to disconnected, to avoid flickering state on flaky mobile networks.

## 9. Game sessions — restart session boundary

`rounds`/`guesses` are not scoped to `room_id` alone. A room can be restarted (§14 `restart-room`), and each playthrough is its own `game_sessions` row — `rounds.game_session_id` is what actually disambiguates "round 1 of this game" from "round 1 of the previous game in the same room."

- `restart-room` creates a new `game_sessions` row (`session_number` + 1), snapshotting the room's *current* `category_id`/`settings` into it, rather than zeroing/reusing the previous game's `rounds`/`guesses` rows.
- Prior `rounds`/`guesses` rows are left untouched, still attached to their original `game_session_id` — this is what keeps per-round recap, fastest-average-guess-time, most-correct-guesses, MVP, and per-round breakdown correct after a restart (§7), and incidentally sets up a "past games in this room" view later without any schema change.
- `players.score` is reset to 0 on restart; `players` rows themselves persist across sessions (same room, same seats) — restart does not re-create players.

## 10. Kick vs. mute

Kick and mute are different actions with different enforcement points, both host-only (`DESIGN.md` §5):

- **Mute** (`players.is_muted`): stops a player from posting to `chat_messages`. Enforced in the RLS `insert` policy on `chat_messages` (§4), not just hidden in the client — a muted player's guesses (written server-side via `submit-guess`, §14) are unaffected; mute is about chat noise, not gameplay.
- **Kick** (`players.status = 'kicked'`): removes the player from active participation and blocks the automatic `localStorage` rejoin described in §8. A `kick-player` Edge Function (§14, host-only) sets `status = kicked` and `is_connected = false`, and broadcasts a removal event so the kicked client is redirected out immediately rather than waiting for their next action to fail.
- This only blocks the *same* browser session from silently walking back in; it doesn't prevent a determined player from rejoining with a fresh anonymous session. See the open question in §16.

## 11. Host migration

If the connected host's Presence entry drops, the server (Edge Function reacting to the Presence event, or a scheduled check) promotes the longest-connected remaining player to `is_host = true`. This is never a client-side election — a race between two clients both trying to self-promote is exactly the kind of bug this needs to avoid. The UI reflects the change immediately (badge, system chat message) so it's never ambiguous who can start/restart.

## 12. Late joiners

Joining is allowed at any room `status`. If `status = in_progress`, the new `players` row is created with `is_spectator = true`; the Edge Function/RLS layer prevents spectators from calling `submit-guess`. When the current round ends and the next one starts, spectators flip to full players automatically.

## 13. Room lifecycle & cleanup

- Rooms inactive beyond ~24h (`last_active_at` unchanged) are cleaned up by a scheduled Supabase Edge Function / `pg_cron` job — otherwise `rooms` grows unbounded with stale data.
- Server-enforced caps: max players per room, min/max rounds, min/max seconds per round (same validation point as §7).
- Word selection is no-repeat within a session and shuffled per room, so two rooms playing the same category don't see identical sequences.

## 14. Edge Functions (all trusted game logic — Non-negotiable rules 1, 2, 5)

Each uses `service_role` server-side only, never exposed to the client bundle. `create-room` and `join-room` are implemented (`supabase/functions/create-room/`, `supabase/functions/join-room/`); the rest are not yet written.

**Response envelope** (`supabase/functions/_shared/errors.ts`), shared by every function: `{ ok: true, data }` or `{ ok: false, error: { code, message, fields? } }`. Deliberately HTTP 200 for expected *domain* outcomes (validation, wrong password, room full, kicked) — only auth failures (401) and genuine faults (500) get a non-2xx status, since `supabase.functions.invoke()` throws on any non-2xx and buries the body behind `err.context.json()`.

| Code | HTTP | Meaning |
|---|---|---|
| `UNAUTHENTICATED` | 401 | no/invalid JWT |
| `METHOD_NOT_ALLOWED` | 405 | non-POST |
| `VALIDATION_ERROR` | 200 | `fields` maps field → message |
| `PROFANITY_BLOCKED` | 200 | `fields` names the offending field(s) — filter covers room name, custom words (both sides), and display name (extended past DESIGN.md §5's literal list — an unfiltered display name is visible to the whole room for the entire game, same exposure as a room name) |
| `CATEGORY_NOT_FOUND` | 200 | create-room: `categoryId` isn't a real global category (blocks pointing a new room at another room's private custom category) |
| `ROOM_NOT_FOUND` | 200 | join-room: bad code format or no such room — deliberately not distinguished, no format-probing signal to leak |
| `PASSWORD_REQUIRED` | 200 | room is protected, none supplied |
| `INVALID_PASSWORD` | 200 | wrong password |
| `ROOM_FULL` | 200 | active players ≥ `settings.max_players` |
| `KICKED` | 200 | existing player row has `status='kicked'` |
| `CODE_GENERATION_FAILED` | 500 | 5 collision retries exhausted |
| `INTERNAL_ERROR` | 500 | anything unhandled |

- `create-room` — validates + profanity-checks display/room name and custom words, clamps settings, verifies the category, hashes the password (if any), generates the room code with a collision-retry loop (catches `23505`, regenerates, ≤5 attempts), creates the room + optional custom category/words + host player. Any failure after the room insert triggers a compensating delete (`ON DELETE CASCADE` cleans up categories/words/players in one statement) — supabase-js has no cross-table transaction primitive, and moving this into a single SQL function would pull trusted logic out of the testable `_shared/` modules, so this is a deliberate trade-off, not a shortcut.
- `join-room` — looks up the room by normalized code, checks for an existing `players` row *before* the password gate: a `kicked` status short-circuits to `KICKED`; an existing **active** seat skips the password check entirely and goes straight to a rejoin update. This is deliberate: the existing seat is proof the password (if any) was already satisfied once, and it's what makes DESIGN.md §2.9's silent-refresh-reconnect promise work without re-prompting for a password on every refresh. New joins get `is_spectator = true` when `room.status !== 'lobby'` (§12/§2.7), and never `is_host: true` (the `players_one_host_per_room` partial unique index would reject it anyway — the schema backstopping the application logic). A `23505` race on the seat's unique constraint falls through to the same rejoin-update path rather than failing.
- `start-round` — selects next word (no-repeat/shuffled), writes `started_at`/`ends_at`, broadcasts.
- `submit-guess` — the core function described in §3. A partial unique index enforces the invariant from §7:
  ```sql
  CREATE UNIQUE INDEX guesses_one_correct_per_player_round
    ON guesses (round_id, player_id)
    WHERE is_correct = true;
  ```
  This closes the race between two near-simultaneous requests from the same player that could otherwise both evaluate "not yet correct" before either write lands and double-award the first-guess bonus. The function must catch the resulting unique-violation as an expected "already answered correctly" outcome — return the existing result, award no additional points — rather than surfacing it as an unhandled error.
- `advance-round` — triggered on timer expiry or all-correct; writes recap data, advances `round_number` or ends the game.
- `restart-room` — creates a new `game_sessions` row and resets `players.score`, per §9. Does not touch or delete prior `rounds`/`guesses`.
- `kick-player` — host-only; sets the target player's `status = 'kicked'`, `is_connected = false`, and broadcasts a removal event (§10).
- `cleanup-rooms` — scheduled, per §13.

## 15. Pure logic vs. network code

Scoring formulas and string normalization are unit-testable independent of any Edge Function or UI (Coding conventions) — but "lives in `lib/`" turned out to mean something more specific once Edge Functions actually existed. Deno (Edge Functions) and Next can't share a plain `src/lib/` module directly, and `mcp__supabase__deploy_edge_function` only bundles files under a function's own upload set, so the canonical home is **`supabase/functions/_shared/`**: self-contained modules (no relative imports of their own, Web-API-only, no `Deno.*`/`node:*`) imported by Deno via relative path (`../_shared/settings.ts`) and by Next via the `@shared/*` tsconfig path pointing at the same directory. `room-code.ts`, `settings.ts`, `custom-words.ts`, `validation.ts`, `avatars.ts`, `profanity.ts`, `errors.ts`, `cors.ts` all live here; `supabase-admin.deno.ts` is the one Deno-only exception (`.deno.ts` suffix, excluded from Next's `tsc`). Edge Functions import from here rather than reimplementing logic inline, and the same modules back the client-side live-preview validation in the Create Room form — client and server parse/validate identically because it's the same code, not a hand-synced copy.

## 16. Open technical questions (flag before Phase 1 sign-off)
- Exact Presence heartbeat/timeout values for disconnect detection (balance flicker vs. responsiveness).
- Rate limiting on `submit-guess` (per-player, per-round) to prevent guess-spam abuse — related to, but distinct from, the DB-enforced "one correct guess per player per round" invariant in §14, since it's about request volume rather than correctness double-counting.
- Whether a `kicked` player should be permanently blocked from rejoining via a *new* browser session (different `auth_user_id`, same person) — `players.status` (§10) only stops the same session from walking back in, not a determined re-joiner. Left open pending a decision on how strict v1 moderation needs to be.
- Anonymous sign-in abuse prevention: Supabase's own guidance recommends CAPTCHA/Turnstile on anonymous sign-ups before going public, since each `signInAnonymously()` call creates a real `auth.users` row (default-rate-limited to 30/hour per IP, adjustable in the Dashboard). Not needed for local development/testing, but worth doing before a room link gets shared widely.
